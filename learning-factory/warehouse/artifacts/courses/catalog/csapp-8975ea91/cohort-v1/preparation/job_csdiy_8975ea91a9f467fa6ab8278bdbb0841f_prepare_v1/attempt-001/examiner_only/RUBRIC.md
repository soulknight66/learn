# Examiner Rubric — A Trustworthy Byte Histogram

Classification: examiner-only. Do not copy scores, answer guidance, diagnostic cases, or completion thresholds into learner-visible artifacts.

This rubric evaluates only study_unit_csapp_001_trustworthy_byte_histogram, a manager-authored kickoff. It cannot establish completion of CMU CS15213: CSAPP as a whole.

## Validation protocol

Evaluate a frozen submission in an isolated temporary workspace. Do not repair it. Reject build or test behavior that retrieves network resources or reads learner or project data outside the frozen workspace. Allow only the examiner-provided system toolchain, standard headers and libraries, loader/runtime files, and isolated temporary directories assigned to the run. Run subprocesses with argument arrays, bounded timeouts, process groups, and captured logs.

Capture separately labeled evidence for:

- BUILD;
- LEARNER_TESTS;
- FUNCTIONAL;
- SAFETY;
- DOCUMENTATION; and
- COMPREHENSION.

A learner-authored test report is an artifact to assess, never evidence that a command passed. The examiner must run the build, learner tests, and an independent suite. Suggested bounds are 60 seconds for the build, 120 seconds for learner tests, and 10 seconds per functional case. Retain failure logs.

## Required gates

The unit is not complete unless all of the following hold:

1. make clean all succeeds with the published strict warning flags.
2. make test succeeds and contains meaningful automated assertions.
3. Essential independent cases pass: empty input, embedded NUL and high bytes, exact report format and order, unavailable input, and invalid argument count.
4. Input processing uses memory bounded independently of input size.
5. Available undefined-behavior and memory diagnostics report no defect.
6. Every path required by STUDY_TASK.md is present in the specified location and nonempty where applicable; tests/ contains meaningful automated test material, and the documentation and comprehension responses are internally consistent.
7. No prohibited retrieval, external-workspace dependency, fabricated evidence, unsafe cleanup, or false-success exit is observed.

A build failure caps the score at 30. A missing or non-meaningful learner test target caps it at 69. A safety defect, unbounded whole-input buffering, fabricated evidence, destructive cleanup, or a status-0 failure result prevents completion regardless of total.

## Scoring

### Functional contract — 40 points

- 10: Correct reports for empty and ordinary standard-input and file-input cases.
- 8: Correct handling of arbitrary bytes, including 00, 7F, 80, FE, and FF.
- 7: Exact total line, uppercase two-digit keys, decimal counts, ascending nonzero rows, and newline termination.
- 7: Identical results across varied read boundaries and a multi-megabyte input within resource bounds.
- 8: Correct usage, open/read/output failure behavior, diagnostics, exit statuses, and suppression of a premature report.

Independent cases should include sizes around several likely buffer boundaries, repeated high bytes, all 256 byte values in a nontrivial order, a path containing spaces, and redirected standard input. Where the platform safely supports it, induce a post-open read failure and an output failure. Do not penalize platform-dependent diagnostic wording beyond the published prefix and required behavior.

### C and software design — 20 points

- 4: Histogram state and command-line/process concerns are separated through a coherent header contract.
- 4: Input is processed incrementally with bounded memory and without text assumptions.
- 5: Short reads, EOF, read errors, writes or flushes, resource cleanup, and exit decisions are handled deliberately.
- 3: Per-bin and total overflow are explicitly guarded without partial successful reporting.
- 4: The strict build is warning-free; code has no observed undefined behavior, invalid access, leak, or unsafe byte indexing.

### Learner tests — 15 points

- 3: make test is repeatable, bounded, and returns a truthful status.
- 7: The suite covers standard input and file input, empty and binary data, high bytes, ordering, usage failure, unavailable input, and multiple boundary sizes.
- 3: Expected outputs are fixed independently or generated by an evidently independent oracle; tests fail for plausible faulty variants.
- 2: Fixtures and temporary outputs are isolated and cleaned without broad deletion.

### Documentation and evidence — 10 points

- 2: README commands are sufficient to reproduce build, test, and use.
- 4: DESIGN states contracts, invariants, responsibilities, failure and overflow policies, and module rationale consistently with the code.
- 3: TEST_REPORT names the actual environment and commands, matches examiner-observable artifacts, and states limitations honestly.
- 1: The required tree is complete and any optional references or provenance are disclosed.

### Comprehension — 15 points

- 4: Responses 1–2 correctly reason about initialization, accepted-byte accounting, the sum-of-bins relationship, byte range, and signed-indexing hazards.
- 4: Responses 3–5 distinguish progress, EOF, and error; explain chunk-boundary independence; and reason about report timing and observable failure.
- 4: Responses 6–7 explain overflow as semantic corruption and critically assess an independent test oracle and its limits.
- 3: Responses 8–9 reason coherently about separation of concerns and trace a real requirement across design, code, test, and evidence.

For question 2, full-credit reasoning recognizes that every possible input byte must map to an index in the inclusive range 0 through 255; a signed character path can produce a negative or otherwise invalid index. For question 3, full credit requires examining stream state after processing any bytes actually returned rather than treating every short transfer as either immediate EOF or immediate failure. For question 7, round-tripping or reusing production counting logic alone is not an independent oracle. Do not award comprehension credit for conclusions contradicted by the learner's artifacts.

## Completion decision

Record UNIT_SUCCEEDED only when:

- the total is at least 80 out of 100;
- Functional Contract is at least 32 out of 40;
- C and Software Design is at least 14 out of 20;
- Comprehension is at least 10 out of 15; and
- every required gate is satisfied.

Otherwise record UNIT_NOT_YET_COMPLETE with evidence-linked findings. In either case, explicitly record that the result applies only to study_unit_csapp_001_trustworthy_byte_histogram. Only a worker-harness-controlled validator may promote the recorded unit state; the rubric or examiner's prose alone is not promotion evidence.
