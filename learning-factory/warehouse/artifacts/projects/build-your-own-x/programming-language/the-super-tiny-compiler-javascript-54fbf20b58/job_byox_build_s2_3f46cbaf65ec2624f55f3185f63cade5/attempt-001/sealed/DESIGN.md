# Reference design answers

1. **Initializer before scope.** The analyzer visits an initializer before inserting the declaration into its binding map. `let x = x;` therefore reports an unknown identifier instead of reading an uninitialized value. Recursive bindings would need a predeclaration pass plus an explicit policy for initialization cycles.

2. **Precedence and associativity.** `parseTerm` delegates operands to `parseFactor`, so factors finish before `+` or `-` can consume them. The shared loop makes binary levels left-associative. Right-associative exponentiation would parse one left operand, optionally consume `**`, and recurse into the same precedence function for its right operand.

3. **Binding IDs.** Syntactically valid Ripple names can still be JavaScript keywords, global-property names, or future reserved words. Analysis maps declarations and reads to numeric IDs; generation emits `v_0`, `v_1`, and so on. Source spelling never occupies a JavaScript binding position.

4. **Unsafe folding.** A rewrite must not eagerly evaluate a branch that short-circuiting would skip. A call such as `len(7)` may throw at runtime and is not a constant merely because its argument is literal. Division or remainder can produce non-finite numbers that the literal emitter intentionally rejects. The reference folds only literal unary/binary trees and retains non-finite results as operations.

5. **Non-mutation evidence.** Tests serialize the input before and after optimization and check distinct identities at the program, statement, and identifier levels. Recursive reconstruction in `optimize` creates new nodes and location objects even when no fold occurs.

6. **Length policy.** Ripple counts Unicode code points using spread iteration. That makes an astral symbol count once and needs no dependency, but a user-perceived grapheme such as a family emoji can still count several times. Grapheme counting would need a pinned `Intl.Segmenter` contract or a Unicode-data dependency and version policy.

7. **Semantic drift.** The highest-risk boundaries are strict equality, short-circuit operand return values, negative zero, string escaping, `len`, and built-in arity. The sealed suite evaluates the interpreter and optimized and unoptimized generated bodies for the same corpus.

8. **User-defined functions.** The AST would need declarations, parameters, returns, and probably block nodes. Analysis would need nested scopes and distinct function/value namespaces or first-class callable types. Calls would need user-function arity checks, and both runtimes would need stack and recursion policies.

9. **Service limits.** Source bytes, token count, nesting depth, AST nodes, generated bytes, compilation time, runtime time, memory, and output count all need independently enforced ceilings. Execution must occur in an OS-level sandbox with no ambient authority. `sealed/production/safe-runner.js` demonstrates only compile-time size ceilings and is explicitly insufficient for hostile service use.

10. **Failure phases.** Invalid characters and strings are lexical. Missing punctuation or operands are syntactic. Missing bindings and invalid calls are semantic. A checked `len(3)` is structurally valid but fails only if evaluated, so it is a runtime type failure. Keeping these categories stable helps tools decide whether recovery is plausible.
