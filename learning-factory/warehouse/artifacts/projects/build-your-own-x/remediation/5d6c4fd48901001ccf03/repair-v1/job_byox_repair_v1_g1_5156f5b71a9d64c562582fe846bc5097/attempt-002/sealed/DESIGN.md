# Minibox reference design

This document describes the independently generated reference design. Minibox is an educational
Linux container-runtime exercise, not a security boundary suitable for hostile multi-tenant work.

## Scope and contract

The runtime accepts a strict `ContainerSpec`, prepares an execution plan, records lifecycle state,
and delegates execution to an injected backend. A specification includes a root filesystem,
argument vector, environment, hostname, network mode, and timeout; the runtime accepts a separate
container identifier for state ownership. The defaults are
an empty environment, hostname `minibox`, network mode `none`, and a 30-second timeout.

Successful backend execution returns an `ExecutionResult` containing an integer exit code and byte
strings for standard output and standard error. Infrastructure errors are distinct from a program
that ran and returned a nonzero status.

The intentionally small feature set excludes images, layers, registries, overlay filesystems,
cgroups, interactive terminals, daemon APIs, checkpointing, and orchestration.

## Separation of responsibilities

The design has five boundaries:

1. **Specification validation** rejects ambiguous types and values before filesystem or process
   work. Identifiers cannot select state files outside the state directory; `argv` is nonempty;
   timeouts are finite and positive; and only supported network modes are accepted.
2. **Rootfs command resolution** turns a command or `PATH` lookup into one executable inside the
   selected root filesystem. Traversal is rejected. Every symbolic link in the candidate path is
   rejected, including a link that currently resolves inside the rootfs. The result must be a
   regular executable file.
3. **Namespace planning** is deterministic data, separate from execution. Its canonical namespace
   tuple is `user, mount, pid, uts, ipc`, followed by `net` only for network mode `none`. The helper
   invocation is an argv vector, never a shell command string.
4. **State storage** owns durable lifecycle evidence. A record has `container_id`, `status`,
   `revision`, `created_at`, `updated_at`, `exit_code`, and `error` fields. Legal transitions are
   only `CREATED -> RUNNING` and `RUNNING -> EXITED|FAILED`.
5. **Backends** consume the validated plan. Tests can inject a deterministic fake; an optional Linux
   backend invokes `unshare` and sends one strict JSON payload to its helper over standard input.

This split keeps policy testable without requiring root privileges or namespace support.

## Execution sequence

The caller constructs a validated specification before invoking the runtime. For a new identifier,
the runtime creates `CREATED`, transitions it to `RUNNING`, invokes the backend, then records one
terminal outcome. The Linux backend resolves the executable after `RUNNING` is durable, so lookup
failure is preserved as `FAILED` evidence rather than leaving no record. Backend exceptions,
including launch, I/O, and timeout exceptions, become `FAILED`; any `ExecutionResult` becomes
`EXITED`, even when its exit code is nonzero. Terminal records are not silently retried or rewritten.

The subprocess backend does not infer setup success from exit code alone. It creates a bounded status
pipe and passes only its write descriptor through `unshare`. The helper marks that descriptor
close-on-exec, emits `READY` after setup and immediately before `execve`, and emits `ERROR` if setup
or `execve` raises. A successful exec closes the descriptor in the kernel. Missing, malformed, or
error status makes the backend raise and the runtime record `FAILED`; an exact ready status means the
returned process status belongs to the executed workload. A target returning 125 therefore remains a
normal `EXITED` result, while the helper's own 125 after an error is `FAILED`.

State timestamps are generated by the store, not accepted from backend prose. Each accepted
transition increments `revision`; an invalid predecessor is an error. Operations for one identifier
are serialized with `flock` on a no-follow regular lock file. Creation writes and syncs a secure
same-directory temporary inode, then atomically hard-links it at the absent record name; an existing
name remains an error. An update writes a same-directory, no-follow, exclusively created temporary
regular file, syncs it, publishes it with `os.replace`, and syncs the directory. Readers therefore
see no/new complete state on creation, or old/new complete state on transition, never an intentionally
streamed partial document.

The atomic link or replacement is the visibility commit point. A failure before it is an ordinary
`StateError` and cannot expose the proposed record. A directory-sync failure after it cannot be
honestly reported the same way: the new complete record is already visible while crash durability is
unknown. The store raises `StateCommitUncertain` carrying that exact proposal. `recover` locks the
same identifier, verifies that the visible record exactly matches the proposal, retries the
directory sync, and returns it. It never rewrites missing, different, or superseded evidence. A
controller must retain its intent and reconcile after a crash rather than blindly replay a mutation.

The optional subprocess backend uses an argv array and a bounded timeout. The payload travels over
stdin rather than through quoting-sensitive command-line interpolation. `unshare` establishes the
requested namespaces and forks for PID-namespace semantics before the helper performs in-namespace
setup. The launcher does not copy the caller's host environment wholesale: it supplies a fixed
locale, deterministic Python settings, a fixed host tool path, the package root needed to import the
helper, and the status descriptor. The target later receives only the guest fallback `PATH` plus the
specification's environment. The helper then:

1. makes mount propagation private;
2. sets the hostname in the new UTS namespace;
3. drops supplementary groups when permitted, then sets namespace-root gid and uid;
4. enters the validated root with `chroot` and changes to `/`;
5. verifies that `/proc` is a real directory and mounts proc with `nosuid`, `nodev`, and `noexec`;
6. enables `no_new_privs` and installs a restrictive umask;
7. reports readiness over the close-on-exec status descriptor; and
8. replaces itself with the target using an argv vector and the specified environment, reporting an
   error if the exec itself fails.

Network mode `none` means a new network namespace with no host-network attachment configured by
Minibox. It does not promise a loopback interface, DNS, firewall policy, or egress.
Network mode `host` deliberately omits the network namespace and therefore does not isolate the host
network stack.

## Trust boundaries and invariants

The rootfs and command are untrusted inputs. Host-side command resolution must never use the host's
`PATH`, follow a rootfs symlink, or accept `..` to escape the selected tree. Backend payloads are
validated again at the privilege boundary: JSON syntax alone is not authorization.

The state directory is trusted runtime storage, but its contents may be stale or damaged. A prose
message, process exit alone, or backend claim cannot produce `EXITED`; only the runtime-controlled
state transition can do so. Corrupt records fail closed and should be retained for diagnosis.
Post-publication sync failures are separately typed because API failure alone does not imply that no
revision became visible.

Dependency injection is part of the safety model as well as a testing convenience. Unit tests can
assert the exact plan and state sequence without granting namespace or chroot privileges. The real
backend is optional because many CI environments prohibit user, mount, or PID namespaces.

## Deliberate limits

Rejecting all symlinks gives a simple, auditable learner rule but does not eliminate every path race.
There is a check-to-use interval between host-side inspection and execution in the child. `chroot`
is also not a complete containment primitive for a process retaining sufficient privilege. The
reference does not claim cgroup enforcement, capability minimization, seccomp, LSM policy, a
non-root target identity, or sealed rootfs ownership. Same-ID state access is locked, but there is no
cross-record transaction or reconciler. Returned output is capped, yet the subprocess first spools
output to temporary files without a disk quota. These limits are documented in
`production/PRODUCTIONIZATION.md`.
